# 问题记录 Skill

## 概述

高难度理论问题的推导过程冗长，其中的代码和文件内容很容易在对话结束后丢失。本 skill 只负责把**核心问题**和**相关项目文件的原文文本**整理成一份 Markdown 文档，保存到项目根目录，方便日后回顾和复现。对话只是定位问题和文件的线索，不是需要完整存档的对象。

## 核心边界

- **文件内容是主体。** 相关代码、配置、文档、数据说明等文件的原文是记录重点；默认完整收录直接相关文件，而不是只摘录几行或概括其内容。
- **对话只用于定位。** 从对话中提取核心问题、检索关键词、文件路径和用户明确给出的范围即可；不要把完整聊天记录、助手回答或聊天中的推导过程作为正文收录，除非用户明确要求记录对话。
- **记录，不解答。** 不自行计算、推导、调试、验证、解释、归因或判断问题是否正确，也不提出修复方案、建议或下一步行动。
- **原文优先。** 不润色、纠正、格式化、重构或改写文件内容、公式、错误信息和用户原话；不把不确定内容写成确定事实。
- **只记录已经出现的内容。** 信息缺失时写明“对话中未提供”或“未找到相关文件”，不要猜测或补全。
- 如果用户同时要求解决问题和记录问题，记录部分仍只做上述记录工作；除非用户明确要求把解答存档，否则不在文档中新增解题内容。

## 触发时机

**仅显式触发。** 用户明确要求将问题记录成文档时才使用本 skill，例如：

- "把这个问题和代码记录到文档里"
- "把我的问题和相关代码写入 markdown 存档"
- "把这个整理成 md 文件放项目根目录"
- "记录一下这个问题"

以下情况**不要**使用本 skill：

- 用户只是提问或讨论问题，没有提到任何记录/存档/写文档的意图
- 用户要求的是其他整理形式（如归档到 Obsidian 知识库）
- 用户在要求"解释"、"总结"而非"落盘成文件"

判断标准：用户是否明确表达了"把内容写入文件"的意思。不确定时，先做任务主体，最后问一句是否需要落盘成文档，而不是自作主张创建文件。

## 工作流程

### 1. 确认意图与输出位置

- 确认用户确实要求生成文档文件。
- 输出位置为**当前项目根目录**：优先查找 git 仓库根目录（`git rev-parse --show-toplevel`，或在目录树中向上找 `.git`）；如果没有 git 仓库，使用当前工作目录。
- 如果用户指定了其他位置，以用户指定为准。

### 2. 确定核心问题

回顾整个对话，只提取足以确定记录对象的**核心问题**和文件线索。问题部分应尽量使用用户原话，或做最小的中性整理；它的作用是说明后面为什么收录这些文件，不是让记录者进行分析。要求：

- 用户原话应忠实保留，不润色、不概括、不改写；如果必须整理，限于最小的中性表述，并明确它不是原文。
- 如果问题在对话中演进了，只保留能说明最终记录范围的相关表述；不要把整个对话复制进文档。
- 不要收录助手的回答、推导、判断或建议作为记录主体；只有用户另行明确指定要保存某段对话时，才原样收录并标明说话者。
- 不要为核心问题添加“问题在于”“原因是”“应该如何”等记录者自己的判断。

### 3. 收集项目中相关的代码与其他文件

从**项目**中收集与核心问题直接相关的代码文件及其他文件，不依赖对话中产生的代码：

- 先探索项目结构（目录树、`git ls-files`、按扩展名/关键词搜索等），找出与问题直接相关的源码文件（如正在调试的 `.jl`、`.py` 文件）。
- 读取这些文件，把文件原文放入文档。直接相关的文件默认全文收录，不能只留下函数名或摘要。
- 其他相关的非代码文件（如 `.toml`、`.md`、数据文件、配置文件等）也要收录原文，并标注来源路径。
- 每部分标注来源路径（如 `来源: src/entropy.jl`）。标注来源路径是因为文档是自包含的，未来阅读者需要知道代码来自哪里才能继续工作。
- 文件过大或受到工具限制时，才可以收录明确相关的片段；必须注明文件路径、行号或其他范围，以及未收录的部分。不要用自己的判断补写或概括未收录内容。
- 代码、配置和数据保持原文，不要修复、格式化、重构、运行或解释它们。

### 4. 写入文档

使用以下模板；可以增加用于承载文件原文的客观小节，但不要增加“分析”“结论”“建议”“解决方案”或其他表达记录者观点的章节：

```markdown
# [从用户原话提取的中性主题标题，不添加结论]

**日期**: YYYY-MM-DD HH:MM

## 核心问题

[用户原始表述，忠实保留；只说明记录对象，不写记录者的解答或判断]

## 相关文件原文

### 来源: `path/to/file`

[文件原文，默认完整收录]

### 来源: `path/to/another-file`

[文件原文]

## 收录范围

[仅客观说明收录了哪些文件；如有文件无法访问或只收录部分，注明路径和范围]
```

### 5. 报告

文档写入后，只向用户报告事实：

- 文件保存路径
- 收录了哪些相关文件及其原文范围
- 如果某个项目文件无法访问或只收录了片段，说明具体路径和范围

不要在报告中评价问题、判断代码正确性、复述自己的分析、给出建议或声称问题已经解决。

## 命名规则

按用户原话中的关键词组成**中性主题名**，一眼能看出记录对象，例如：

- `GHZ态纠缠熵推导.md`
- `谐振子含时演化问题.md`

避免使用"问题记录.md"、"文档.md"之类的通用名；不要为了命名加入诊断或结论。同名文件已存在时，追加序号（如 `-2`）或直接询问用户。

## 注意事项

- 文档应尽可能完整，使未来阅读者能仅凭核心问题和相关文件原文重建问题上下文；“自包含”不意味着由记录者补写缺失的解释或答案。
- 只创建用户要求的这一个文件，不要修改项目中的其他文件。
- 代码保持原文，不要顺手"修复"或重构。
- 文档语言与用户对话语言一致（对话用中文则写中文），代码、变量名、函数名保留原文。
- 禁止新增未经用户或文件内容支持的事实、推断、评价、结论、建议和解题步骤。
