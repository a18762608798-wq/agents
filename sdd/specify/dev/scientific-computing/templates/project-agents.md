# 项目工作约定

先读 `.specify/memory/constitution.md` 和 `docs/README.md`；实验定义以各 feature 的 spec 为准。

## 日常修改

- 普通修复、重构和文档修改直接进行，只同步受影响的规范并做相关验证。
- 改变科学参数、观测量、实验流程、输出或验收标准时，先更新对应 spec，再按影响更新 plan/tasks。
- 新建或实质重设计实验走完整 Spec Kit 流程；已有 feature 的维护按影响增量处理。
- 保留 Dxx/Sxx、Contract ID 和既有任务状态；不为整理文档重编号或重建 feature。
- 收尾检查受影响的规范是否同步，简要说明验证与剩余偏离；普通修改不自动展开全项目审计。
- Paper 使用独立 skills，直接维护大纲和正文；文献与理论先核验，新增实验需求返回 Exp。

## 整体对齐

- “检查整个项目是否对齐”：执行 `$speckit-analyze 全项目`，再按需执行 `$speckit-converge 全项目 仅检查`。
- “修复并对齐”：先检查，再按问题所在层使用 specify/clarify、plan、tasks 或实施修改，最后复查。
- 检查覆盖所有 feature、规划与跨实验依赖；不只检查当前指针指向的 feature。
- 只读检查不写 tasks、不改变 feature 指针、不切分支，不自动重跑正式实验或提交真机任务。
- 实现缺口按已确认的科学定义修复；科学意图不明时提出问题并继续不受影响的工作。
- 不通过迁就现有代码、降低验收标准或修改完成记录来消除冲突。
- 报告按“已对齐、存在偏离、未核验”区分，并注明文档检查与实现/结果核验的范围。
- 文件存在和任务勾选不足以证明完成；历史证据核对与本轮重新验证分别说明。
