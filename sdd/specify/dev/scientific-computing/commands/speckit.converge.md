# Converge

## User Input

`$ARGUMENTS`

## 范围选择

- 输入含“全项目”“整个项目”或 `project` 时，检查全项目。
- 明确指定已有 `specs/<feature>` 时只检查该目录；缺省仅读取 `.specify/feature.json` 确定当前 feature。
- 指针缺失或无效时列出已有 feature 请用户指定；不替用户选择、不创建 feature。
- 全项目范围取 `specs/` 中的 feature 目录与 experiment-map 所列实验的并集；包含缺少 spec/plan/tasks 的条目，明确报告缺件、未映射目录和无法解析的归属，不静默跳过。
- 直接读取显式目录；审计不写 `.specify/feature.json`，不调用会持久化 feature 选择的脚本，不切分支。
- Contract ID 与任务 ID 在所属 feature 内核对唯一性；跨 feature 引用带目录或 feature 名。Dxx/Sxx 按项目映射核对，允许已约定的共建产物。

## 执行模式

- 输入含“仅检查”“只读”或 `audit-only`，以及用户只要求检查而未授权收敛修改时，执行只读审计：不修改任何项目文件，包括 tasks 和状态页。
- 显式执行 converge 且未要求只读时，保留任务收敛行为：审计后仅向相应已有 tasks 追加真正缺失的工作。
- 两种模式均不直接修改 spec、plan、代码、测试或正式结果；不降低验收标准，不改写既有完成历史。
- 默认核对已有证据；仅检查模式不执行会写入项目产物的测试或脚本。需要的重新验证单独列出，不自动启动正式计算或真机任务。

## Workflow

1. 对选定范围内每个 feature 读取：

   * `spec.md`
   * `plan.md`
   * `tasks.md`

2. 读取项目 AGENTS.md、live constitution、docs/README.md，以及现有大纲和 experiment-map，并遵守其中约束。

3. 检查当前实际状态，包括适用时的：

   * 实现代码
   * 测试
   * validation
   * 正式运行结果
   * 输出文件
   * 运行记录

4. 本命令是审计与任务收敛阶段。

   不直接修改：

   * `spec.md`
   * `plan.md`
   * 实现代码
   * 测试代码
   * 正式实验结果

5. 对照 spec 检查实际状态：

   * Scientific Description 中的目标和输出是否真正实现；
   * feature Boundary 是否被遵守；
   * 正式运行是否满足适用的 `PRE-*`；
   * `POST-*` 是否有实际结果与 validation evidence 支持；
   * `INV-*` 是否有足够证据表明在要求范围内成立；
   * 全部适用的 `VAL-*` 是否真实执行并通过；
   * 是否存在 invalid run 或未处理失败。

6. 对照 plan 检查：

   * 计划中的必要实现是否真实存在；
   * 关键数值与技术决策是否按计划落实；
   * 验证方案是否真正执行；
   * 是否存在计划已写但实际遗漏的部分。

7. 对照 tasks 检查：

   * 已勾选任务是否确实完成；
   * 是否存在“任务已完成但实际行为缺失”的情况；
   * 是否存在实现过程中产生但尚未记录的必要剩余工作；
   * Validation 任务是否有真实证据支持其完成状态。

8. 如果发现实现层面的缺口，仅检查模式只报告位置与建议；任务收敛模式才将新的、具体可执行任务追加到对应已有 `tasks.md`：

   * 实现缺口 → `Implementation`
   * 验证缺口 → `Validation`

   不删除或重写已有任务，不通过修改已完成任务掩盖历史状态。
   同一缺口已有未完成任务时引用该任务，不重复追加；缺少 tasks 文件时报告上游缺件，不自行生成。

9. 新增任务必须：

   * 直接对应已存在的 spec / plan；
   * 有明确完成条件；
   * 只描述真正缺失的工作；
   * 不引入新的实验定义或实现设计。

   新增 Validation task 必须对应已有的 `VAL-*`。

   如果实际审计发现某项 Contract 无法验证，
   但 spec 中不存在相应 Validation 定义，
   这属于 spec gap：

   不得在 converge 中自行发明新的 validation requirement，
   应返回 `specify` / `clarify`。

10. 如果发现的问题实际属于上游定义错误，例如：

    * spec 缺少必要科学定义；
    * plan 与 spec 冲突；
    * 需要改变实验参数、输出或 validation；
    * 必须做出新的科学决定；

    不在 `tasks.md` 中自行解决。

    报告该问题应返回：

    * `specify` / `clarify`；或
    * `plan`

    处理。

11. 如果 spec、plan、tasks 与实际实现和结果已经一致：

    * 不新增任何任务；
    * 不为了形式化修改 `tasks.md`；
    * 明确报告 feature 已收敛。

12. 完成后报告：

    * 是否已收敛；
    * 发现的实现缺口数量；
    * 新增的 Implementation / Validation 任务；
    * 是否存在需要返回上游处理的问题。

## 全项目的跨实验核验

先核对全项目文档关系，再逐 feature 审计实际状态，并检查生产者与消费者之间的衔接：

- 共享数据、参数视图和共建图层是否来自约定的上游产物，版本、元数据及科学约定是否兼容。
- 所需输出是否真实可用，失败或未验证的上游是否仍被下游作为有效输入。
- 任务完成声明是否有对应的验证记录；历史证据能否对应当前定义、实现与产物。
- 文件存在、任务全勾或旧报告通过不能单独证明当前有效；证据缺失或来源无法核实时标记“未核验”。
- 区分“已有证据核对通过”和“本轮执行验证通过”；说明尚未运行的验证及其影响。

统一列出全部 feature 的“已对齐、存在偏离、未核验”状态、跨 feature 问题、证据和应处理的层。
只有检查范围完整且必要证据充分时才能报告全项目已收敛；部分通过不得代替全项目结论。
仅检查模式报告建议任务；任务收敛模式另列实际追加的任务。报告默认直接回复，不自动生成看板或另一套项目状态文件。

## 修复路由

实验定义或缺失的科学决定返回 specify/clarify，实现设计返回 plan，任务拆分返回 tasks。
实现缺口按已有 spec/plan 实施并验证。用户明确要求“修复并对齐”时依次处理已授权范围并复查；
科学意图不明时先提出问题，不让代码现状反向定义实验。
